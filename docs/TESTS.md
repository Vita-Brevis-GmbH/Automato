# Tests und CI

Was wo geprüft wird – lokal und in der CI (`.github/workflows/ci.yml`). Alle Tests laufen
gegen Testdaten (anonymisiert, `example.ch`, „Kunde A“), nie gegen echte Systeme.

| Ebene | Was | Lokal | CI-Job |
|---|---|---|---|
| Lint | ruff (Python), tsc (Frontend), PowerShell-Syntax der Agent-Skripte | `uv run ruff check .`, `uv run ruff format --check .`, `npm run lint`, `pwsh scripts/check_powershell.ps1` | `python`, `frontend` |
| Unit/API | Orchestrator (FastAPI-TestClient, SQLite), Collectors (Normalisierung, Clients mit Fakes), SoT-Gateway (Nur-Lese-Schutz, NetBox-Schreiber) | `uv run --package <paket> pytest <paket>/tests` | `python` (Abdeckung ≥ 90 % je Paket) |
| Postgres | Migrationen hoch/ganz runter/hoch, **`alembic check`** (Modell = Migrationen), alle Orchestrator-Tests gegen Postgres 16 | `AUTOMATO_TEST_DATABASE_URL=postgresql+psycopg://…` | `postgres` |
| NetBox-Sync | Fake-NetBox mit Eindeutigkeit wie NetBox (VLAN-Name je Gruppe, Site-Name), auch Abschnitt Virtualisierung (Cluster, VMs, VM-Interfaces, IPs) | in `orchestrator/tests/test_netbox_sync.py`, `test_vmware.py` | `python`, `postgres` |
| VDOMs | FortiGate mit zwei VDOMs (gleiche Policy-IDs, Objekt- und VIP-Namen): Collector liest je VDOM (`vdom=`), VDOM ohne Leserecht in der Meldung; Orchestrator: Verweise, Gruppen, NAT, Paare, Befunde je VDOM | `collectors/tests/test_fortigate_client.py`, `orchestrator/tests/test_vdom.py` | `python`, `postgres` |
| Routing | FortiGate je VDOM (ECMP, BGP-Pfade inkl. Backup, statische/Policy-Routen, SD-WAN, HA/FGSP ohne Passwort/PSK, fehlende Rechte, seitenweise Monitor-Listen), ACI (L3Out mit vPC-SVI und BGP-Peer ohne Passwort, Border-Leaf-Routen); Orchestrator: Speichern je Lauf, längstes Präfix, Weg für IP mit Policy-Routen, Mandant, Löschen; Weg Hop für Hop (Quelle angeschlossen bzw. im Fabric, gewählter Start, ECMP nach extern, Policy-Route sicher/möglich, L3Out-SVI als Nachbar, Ende im Fabric), Bezeichnungen Firewall/VDOM/VRF, VDOMs je Quellsystem, IPAM-Namen der Nachbarn (auch Netz mit Beschreibung); VRF/Management getrennt (Collector und Weg), kein Raten über ein gemeinsames Transfernetz (zwei Firewalls am selben Aussenrouter); Regeln auf dem Weg (erste sichere Policy entscheidet, Dienst, Zone/Interface, FQDN und Benutzergruppe nur möglich, abgeschaltete zählen nicht, implizit gesperrt, Start ohne Quelle); NAT auf dem Weg (VIP mit Port-Weiterleitung zur internen IP, SNAT-Pool als Quelle für die innere Firewall, VIP nur am eigenen Interface); Relevanz in der Doku (Regel „lan → internet, any“ für einen DMZ-Server nicht möglich als Ziel und Quelle, „lan → dmz“ als Ziel möglich, als Quelle nicht; Doku je System ohne die unmöglichen, mit Begründung; Applikations-Doku mit Relevanz je Treffer, Kennzahlen und Export ohne sie); Gegenstelle any als Netze hinter dem Interface, Default-Route bzw. Internet-Anbindung (Kategorie 2) | `collectors/tests/test_routing.py`, `orchestrator/tests/test_routing.py`, `orchestrator/tests/test_paths.py`, `orchestrator/tests/test_policy_check.py`, `orchestrator/tests/test_relevance.py` | `python`, `postgres` |
| Parallele Firewalls | Verbund aus Vorschlag (Session-Sync, gleiche Policies) bzw. Quellsystem: gleiche Policies einmal, abweichende beide mit Feldern, fehlende markiert, Kennzahlen ohne Zwillinge, Findings (Regel abweichend/fehlt, Objekt anders), Verbund auflösen; Vorschlag ablehnen, Verbund auflösen = ablehnen, rückgängig, von Hand gesetzter Verbund hebt die Ablehnung auf; redundante Wege (BGP-Backup gleicher Länge, schwebende statische Route +1 Hop, abgeschaltete nicht, Filter nach Länge, ECMP über einen Verbund); Anbindungen nach aussen (Internet über Next-Hop, MPLS über Interface mit manueller Route zum anderen Standort, Netze dahinter, Rechte, Löschen mit dem Quellsystem, für mehrere Firewalls); erkannte Anbindungen (vier WAN-Router mit BGP an zwei Firewalls eines Verbunds = ein Vorschlag mit aktiv/Backup/AS, ohne Management-Tabelle und gelesene Nachbarn, andere Firewall eigener Vorschlag, teilweise abgedeckt, Zustand mit nicht eingetragenen Routern, Router n von N, ausblenden und wieder anzeigen mit Rechten); Länge der Wege (gleich lang/+1 Hop) | `orchestrator/tests/test_parallel.py`, `orchestrator/tests/test_paths.py` | `python`, `postgres` |
| Agent-Update | veralteter Agent bekommt neue Läufe erst nach dem Update (bzw. nach 10 min), aktualisiert sich sofort; nur ein Update gleichzeitig, fehlende Dateien nachinstalliert, Rückfall auf die zuletzt guten Pakete (`collectors/tests/test_selfupdate.py`); Upload mit langer Wartezeit und Wiederholung, Teil-Uploads nicht doppelt, Lesen wiederholt bei Timeout/503 (`sot-gateway/tests/test_netbox_adapter.py`), Orchestrator quittiert einen abgeschlossenen Lauf nur (`orchestrator/tests/test_internal_ingest.py`) | `orchestrator/tests/test_agent_update.py`, `collectors/tests/test_run.py` | `python`, `postgres` |
| VMware | Nur-Lese-Schutz (WSDL-Name, z. B. `Destroy_Task` blockiert), Abruf über nachgebaute pyVmomi-Verbindung, Normalisierung; Orchestrator: Portgruppe → EPG, Befunde, VMs in Regeln/Doku | `collectors/tests/test_vmware.py`, `orchestrator/tests/test_vmware.py` | `python`, `postgres` |
| UI (E2E) | Playwright: jede Ansicht ohne Seiten-/API-Fehler, Kernabläufe (Suche, NAT-Links, Findings, Dienste, Standorte, IPv4/IPv6-Paare und gleichnamige Objekte, Virtual Server, Regeln je Subnetz, VMware-VMs mit EPG, Alle einlesen inkl. Abbrechen & neu starten, Ports je Gerät, Ports kompakt mit Detail, Portgruppe im Detail, Läufe mit Filtern, Paar bestätigen, VIP-Ziel, Betriebszustand, NAT-Prüfung, VM im Regel-Detail, Applikations-Doku mit Filtern und Erklärung, Stammdaten, VDOM-Filter und Objekte je VDOM, Firewall nur mit root ohne „VDOM root“, Routing: Weg für IP je Kontext und Hop für Hop mit Quelle bzw. Startpunkt, IPAM-Namen, Kontext-Filter mit Firewall, BGP-Backup, HA, L3Out, Anbindung aus einem Weg erfassen, Wege im Überblick mit ECMP und Backup, erkannte Anbindung ausblenden und wieder anzeigen, mit allen Routern übernehmen (Sprung zum Formular), Wege gleich lang, Regeln auf dem Weg (gesperrt bzw. abhängig mit Dienst, DNAT zur internen IP, Link zur Policy); Doku je System ohne routingtechnisch unmögliche Regeln, mit Begründung, Gegenstelle any als Netze bzw. Default-Route; parallele Firewalls per Vorschlag zusammenfassen mit Abweichungen und Findings, Verbund auflösen und wieder vorschlagen) gegen Orchestrator + Vite mit Beispieldaten (`web-ui/frontend/e2e/`) | `cd web-ui/frontend && npm run e2e` | `e2e` (Bericht als Artefakt bei Fehler) |
| Leistung | Grosses erzeugtes Regelwerk (Standard 3000 Regeln, 8000 Hosts): Einlesen und Abfragen messen – nur lokal, leere Datenbank | `AUTOMATO_DATABASE_URL=… uv run --package orchestrator python scripts/bench_large_ruleset.py` | – |
| Images | Compose-Konfiguration aller Profile, Agent-Paket, Images Orchestrator/Collector/Web-UI | `docker compose --env-file .env.example … config --quiet` | `docker` |
| Secrets | gitleaks über die ganze Historie | – | `gitleaks` |

Die Jobs laufen bei jedem Push nur für geänderte Komponenten; **nächtlich** (02:17 UTC) und
über *Run workflow* (workflow_dispatch) laufen alle.

**Neue Funktion → neuer Test:** Backend-Logik als Orchestrator-/Collector-Test (Testdaten in
den Testmodulen, wiederverwendet von `e2e/seed.py`), sichtbare Abläufe zusätzlich in
`web-ui/frontend/e2e/flows.spec.ts`. Schemaänderung = Alembic-Migration (sonst schlägt
`alembic check` fehl).
